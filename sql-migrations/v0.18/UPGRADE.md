# Upgrade to EDC 0.18.1 (DSE 0.7.x → this release)

DSE moves from EDC Connector 0.16.1 / IdentityHub 0.16.0 to **EDC 0.18.1** (Connector, IdentityHub, IssuerService, FederatedCatalog) and Technology-Azure 0.18.0. Tracking ticket: PSMP-5859 (implementation); impact study: PSMP-5858.

## Upgrade order
1. **Back up** the participant databases (consumer / provider), the authority database and the vault secret `<participant>-aes` of every IdentityHub, IssuerService and telemetry-agent.
2. **Run the SQL migration while 0.7.x is still running.** The scripts are additive and idempotent, and 0.7.x keeps working on the migrated schema:
   ```bash
   ./apply-migrations.sh --host <db-host> --port <port> --user <superuser> --pass <password>
   # participant-migration.sql -> consumerdb, providerdb ; authority-migration.sql -> authoritydb
   ```
3. **Roll out the new images together with the new charts and configuration.** Swapping images alone is not an upgrade (see "Configuration changes"). Where the DIDs lose their port, continue at once with "DIDs without port: re-onboard the participants" below: its step 1b re-keys the control-plane data, before the credentials are requested again (step 2).
4. Verify the following:
   - no `SEVERE` / `EdcException` in the control plane, data plane, IdentityHub and IssuerService logs;
   - existing agreements and transfers are readable;
   - the existing offers are in the provider's catalog;
   - a new negotiation reaches `FINALIZED`.

The data-plane tables `edc_accesstokendata` and `edc_data_plane` are **not** in the SQL scripts on purpose. The data plane creates them at its first start (`EDC_SQL_SCHEMA_AUTOCREATE=true`, the chart default), owned by the participant DB user. If you create them as a superuser instead, the data plane fails at boot with `must be owner of relation edc_accesstokendata`. If autocreate is disabled, create them **as the participant user**, using the upstream 0.18.1 files `accesstoken-data-schema.sql` and `dataplane-schema.sql`.

The upstream CEL store and task store SQL modules (`cel-expression-schema`, `edc_tasks`) are not on any DSE runtime classpath, so those schema changes do not apply here. The IdentityHub `credentials-schema.sql` is unchanged between 0.16 and 0.18.1 apart from a comment.

## Rollback
Redeploy the 0.7.x images **and** the 0.7.x charts / configuration. The schema needs no DB step: the new columns and tables are ignored by 0.7.x (`rollback.sql` is documentation only). The new configuration below cannot be used with the old images, because 0.16.1 only reads the `edc.iam.trusted-issuer` prefix. The 0.7.x configuration also brings back the old DIDs (with port), so agreements negotiated with the new DIDs cannot be used after the rollback. The data needs up to two DB steps, right before redeploying the old images (after the DID document services, see below, if they were synced):
- if the control-plane data was re-keyed (re-onboarding step 1b), run `participant-rekey-did-rollback.sql` on each participant database, with the same `old_did` / `new_did` and the same `psql` call as in step 1b (`-f participant-rekey-did-rollback.sql`). 0.7.x serves only the rows keyed by the old DID. The script moves every row keyed by the new DID back, including those created on 0.18.1, and a second run reports `0` rows. The fallback is the participant database backup of "Upgrade order" step 1, which loses what was created since;
- if the old holders and attestations were already deleted (re-onboarding step 2b), restore the authority database backup of "Upgrade order" step 1, because 0.7.x needs them.

If the DID document services were already migrated with `syncServices` (e.g. the authority `FederatedCatalogService` now points to `/api/management/v4/catalogs/request`, which the 0.7.x federated catalog does not serve), restoring the 0.7.x configuration after the downgrade is not enough: the 0.7.x IdentityHub never updates the services of an existing participant. **Before** redeploying the old images, while the new IdentityHub is still running, set `edc.ih.api.superuser.services` back to the 0.7.x values (e.g. `FederatedCatalogService` = the legacy `/api/catalog/v1alpha/catalog/query` URL on port 8383) with `syncServices=true`, restart it, and check that the DID document was published again with the legacy endpoints. Then roll back.

Also when rolling back:
- `helm upgrade` from the new to the 0.7.x telemetry-service and telemetry-agent charts fails (`The order in patch list: [... EDC_IAM_DID_WEB_USE_HTTPS ...] doesn't match $setElementOrder list`: these 0.7.x charts set that variable twice). Uninstall and install these releases again, or upgrade them with `--force`.
- The 0.7.x devbox keygen Job writes a new `<participant>-aes`; if your 0.7.x deployment does the same, put the value backed up in "Upgrade order" step 1 back after the rollback. It encrypts the participant-context configuration written by 0.18.1, which a re-upgrade reads again.
- After the authority database restore, the IdentityHubs set the credentials issued on 0.18.1 to `ERROR` (their status list is gone). This is harmless: 0.7.x uses the old credentials, and a re-upgrade requests new ones (re-onboarding step 2).

## DIDs without port: re-onboard the participants
Every DID with a port changes: `did:web:<p>-identityhub%3A8383:api:did` becomes `did:web:<p>-identityhub:api:did` (chart default, system tests, and the CLE ArgoCD deployments, which set this format in `global.identityHub.didWebUrl`). The DID is the participant identity: participant context id, `edc.participant.id`, STS client id, vault aliases (`<DID>-sts-client-secret`, `<DID>#my-key`), holder id and credential subject. Existing participants are therefore re-onboarded:
1. Deploy every component of the authority and of the participants with the new DIDs (`global.identityHub.didWebUrl`, `global.authority.didWebUrl`, `edc.iam.trustedissuer.authority.id`, ...) and the new service URLs below. At startup the IdentityHub creates the participant context and the DID document of the new DID. The old participant context is no longer used.

   **1b. Right after the rollout, before step 2: re-key the control-plane data of each participant to its new DID.** 0.7.x keyed the assets, policy definitions, contract definitions, negotiations, agreements, transfer processes and EDR entries by the old DID (`participant_context_id`), and the 0.18.1 control plane serves only the participant context of its own DID: without this step its catalog offers none of the existing assets (dataset request `404 Dataset ... does not exist`), and its protocol services do not find the existing negotiations, agreements and transfer processes. Run `participant-rekey-did.sql` once per participant database, each time with the two DIDs of that participant only:

   | Participant database | `old_did` | `new_did` |
   |---|---|---|
   | provider (devbox `providerdb`) | `did:web:provider-identityhub%3A8383:api:did` | `did:web:provider-identityhub:api:did` |
   | consumer (devbox `consumerdb`) | `did:web:consumer-identityhub%3A8383:api:did` | `did:web:consumer-identityhub:api:did` |
   | every other participant `<p>` | `did:web:<p>-identityhub%3A8383:api:did` | `did:web:<p>-identityhub:api:did` |

   ```bash
   psql -X -v ON_ERROR_STOP=1 -h <db-host> -p <port> -U <superuser> -d providerdb \
     -v old_did='did:web:provider-identityhub%3A8383:api:did' -v new_did='did:web:provider-identityhub:api:did' \
     -f participant-rekey-did.sql
   ```
   In one transaction, it replaces the value `old_did` (exact match only) with `new_did` in `participant_context_id` of `edc_asset`, `edc_policydefinitions`, `edc_contract_definitions`, `edc_contract_negotiation`, `edc_transfer_process`, `edc_edr_entry` and in `agr_participant_context_id` of `edc_contract_agreement`, and prints for each column the rows of both DIDs before and after. It changes nothing and fails if a variable is missing, both are equal, `new_did` contains `%3A`, or one of the DIDs is not in `participant_context` of that database (the new one is there once the new IdentityHub has started). It does not change the IdentityHub tables, the counterparty ids and policies (see step 4), or the data-plane tables (the data plane registers with the new participant context at startup). Check:
   - a second run reports `0` re-keyed rows;
   - only `new_did` is left, e.g. `SELECT participant_context_id, count(*) FROM edc_asset GROUP BY 1;` (`agr_participant_context_id` for `edc_contract_agreement`);
   - after step 2, the provider's catalog lists the existing assets under the new DID: consumer `POST /api/management/v4/catalog/request` with `counterPartyId` = the provider's new DID, and the federated catalog after its next crawl.
2. On the authority, create the holders and the membership / domain / visibility attestations again with the new DIDs, then request the credentials again from each IdentityHub (`POST /api/identity/v1beta/participants/<DID>/credentials/request`). Credentials issued to the old DID do not match the new identity.

   **2b. Then, on the authority, delete the holders and attestations of the old DIDs** (only once the new holders, attestations and credentials exist). The federated catalog crawls every holder of the IssuerService (`ParticipantTargetNodeDirectory.getAll()`) and the old DIDs still resolve, so without this cleanup every connector is crawled twice, under its old and its new DID (and the old authority holder is crawled too). Use the Issuer-admin API of the authority IssuerService (`https://<authority>-issuerservice:8181/api/issueradmin`):
   1. List the holders and the attestations, and keep the lists (before / after):
      - holders: `POST /api/issueradmin/v1beta/participants/<authority DID>/holders/query`, body `{"offset": 0, "limit": 1000}`. The query returns the holders of the participant context in the path, and 0.7.x created the old holders under the old authority DID: list them with `<authority DID>` = `did:web:<authority>-identityhub%3A8383:api:did` (sent as `%253A`, see below), the new ones with the new authority DID;
      - attestations: `POST /api/issueradmin/v1beta/participants/<authority DID>/attestation-membership/request`, `…/attestation-domain/request` and `…/attestation-visibility/request` (same body; each lists every attestation, with its `id` and `holderId`).
   2. Delete only an explicit allowlist of the retired DSE identities: `did:web:<p>-identityhub%3A8383:api:did` for each known participant `<p>`, plus the old authority holder `did:web:<authority>-identityhub%3A8383:api:did`. Write the list down; do not select by a `%3A` pattern match. Everything else in the lists stays.
   3. For each allowlisted identity, delete its attestations first (those whose `holderId` is that identity, by their `id`; 0.7.x used the DID as id of the membership and visibility attestations and a generated id for the domain ones): `DELETE …/attestation-membership/<id>`, `…/attestation-domain/<id>`, `…/attestation-visibility/<id>`; then the holder: `DELETE …/holders/<identity>`. Each answers `204`. The ids contain a literal `%3A`, and a literal `%` in a path segment is sent as `%25`, so `%3A` is sent as `%253A`:
      ```bash
      # participant context: the old authority DID did:web:<authority>-identityhub%3A8383:api:did, %3A sent as %253A
      IS='https://<authority>-issuerservice:8181/api/issueradmin/v1beta/participants/did:web:<authority>-identityhub%253A8383:api:did'
      # 1. list and keep the output: the old holders, then every attestation
      curl -sS -X POST -H 'Content-Type: application/json' -d '{"offset": 0, "limit": 1000}' "$IS/holders/query"
      for a in membership domain visibility; do
        curl -sS -X POST -H 'Content-Type: application/json' -d '{"offset": 0, "limit": 1000}' "$IS/attestation-$a/request"
      done
      # 3. one allowlisted identity, stored as did:web:consumer-identityhub%3A8383:api:did: its attestations, then the holder
      curl -sS -o /dev/null -w '%{http_code}\n' -X DELETE "$IS/attestation-membership/did:web:consumer-identityhub%253A8383:api:did"
      curl -sS -o /dev/null -w '%{http_code}\n' -X DELETE "$IS/attestation-visibility/did:web:consumer-identityhub%253A8383:api:did"
      curl -sS -o /dev/null -w '%{http_code}\n' -X DELETE "$IS/attestation-domain/<id of its domain attestation>"
      curl -sS -o /dev/null -w '%{http_code}\n' -X DELETE "$IS/holders/did:web:consumer-identityhub%253A8383:api:did"
      ```
   4. Restart the federated catalog (e.g. `kubectl rollout restart deployment/<authority>-federatedcatalog`). Its crawler re-queues every failed crawl, so it keeps crawling the deleted old holders until it restarts (`SEVERE ... Unexpected exception occurred while crawling: did:web:<p>-identityhub%3A8383:api:did ... 401`, about 600 lines per minute in the devbox).
   5. List again: only the allowlisted rows are gone, and the federated catalog has one catalog per participant.

   A rollback to 0.7.x after this cleanup needs the authority database backup of "Upgrade order" step 1: 0.7.x uses the old holders and attestations. The cleanup is not part of `authority-migration.sql`, which stays additive.

   **Temporary shim, remove later**: the `DELETE`s above, and the listing under the old authority DID, work only because of a temporary IssuerService module, `extensions/issuer-service/issueradmin-uri-compliance-shim`. Jetty 12 rejects `%253A` in a path with `400 Ambiguous URI path encoding`; the shim relaxes this check on the IssuerService `issueradmin` port only: that connector allows ambiguous path encoding (`UriCompliance.Violation.AMBIGUOUS_PATH_ENCODING`, no other violation) and its servlet context decodes ambiguous URIs. Every other port (issuance, statuslist, ...) keeps the Jetty defaults. While it is there, the IssuerService logs one `WARNING` at startup (`Temporary shim: the 'issueradmin' context accepts ambiguous path encoding ...`). The shim is removed (module, `settings.gradle.kts` entry, `issuer-service-base` dependency) once the port-ful holders and their attestations are deleted in every environment.
3. Outside the participant databases, the telemetry storage keys the participants by DID as well (`participant_id` table of the authority billing database): add the new DIDs there, as for a new participant, and keep the old rows (the existing telemetry events and reports reference them).
4. Agreements negotiated with the old DIDs keep the old identities (consumer and provider id, policy assigner and assignee): after step 1b they are listed and readable, but the provider refuses a new transfer on them (DSP `404 Not found`: the consumer addresses it to the old provider DID). Negotiate again on the re-keyed offers.

The `DSPMessaging` endpoint (`https://<p>-controlplane:8282/api/dsp/2025-1`) does not change. Where the DID has no port already (e.g. `did:web:<hostname>:webdid` with ingress), the DID and the credentials are kept: only the `CredentialService` / `IssuerService` URLs of the DID documents change (deploy them with `syncServices=true`, see below).

Outside this repository, update `eonax-iac-workflows` (`did_url_base64_url` and the `IssuerService` URL on `/v1alpha` in `terraform/backend/{authority,participant,issuer-service}/identityhub.tf`, the APIM operations on `/v1alpha/participants/...` in `terraform/apis`), `argocd-content-lifecycle-enabler` (`%3A8383` DIDs, base64 `CredentialService` / `IssuerService` URLs) and the Bruno environment values in `dxp-internal-tools` (`authorityBase64DID`, `consumerBase64DID`, `providerBase64DID` are replaced by `authorityDID`, `consumerDID`, `providerDID`, holding the plain DIDs).

## Behaviour changes for operators and API consumers
- **AES key is now persistent data.** `<participant>-aes` encrypts `edc_participant_context_config.private_entries`. Back it up, and never rotate it without re-encrypting. The devbox keygen job now writes it only if it is absent.
- **Log format changed**: lines now look like `INFO 2026-10-14T07:40:41.46… message` / `WARNING …` / `SEVERE …`. Splunk queries and alerts based on the old JDK-logger format must be updated.
- **Identity / Issuer-admin APIs** are served on the upstream `/v1beta/participants/<DID>/…` paths, with the DID as is: e.g. `POST /api/identity/v1beta/participants/did:web:provider-identityhub:api:did/credentials/request`. `/v1alpha` URLs and base64 participant ids return `404` (the temporary `legacy-participant-id-path` rewrite is removed). A DID with a port cannot be used in these paths: its `%3A` would have to be sent as `%253A`, which Jetty 12 rejects with `400 Ambiguous URI path encoding` (only the IssuerService `issueradmin` port accepts it, temporarily, to delete the old holders: re-onboarding step 2b). This is why the DIDs no longer contain the port.
- **Management API v4 only (hard cut, PSMP-11644).** EDC 0.18.1 deprecates every management v3 API; the DSE APIs are v4 only and every DSE tool, test and Bruno request uses v4. Old DSE paths return 404. The upstream v3 APIs are still served: each EDC 0.18.1 module registers v3 and v4 together with no setting to turn v3 off, so block `/api/management/v3` at the gateway if it must not be reachable:

  | Before | Now |
  |---|---|
  | control plane `POST /api/management/v1alpha/catalog/query` (DSE filtering) | `POST /api/management/v4/catalogs/request`: same signature as the federated catalog query API (the two are kept aligned); the response is the catalog filter's reply as is (DSP 2025-1 form, see below), not the federated catalog response. The two endpoints live on different services (the control plane does not load the upstream federated-catalog query API — see below), so sharing the path is safe |
  | federated catalog `POST /api/catalog/v1alpha/catalog/query/count` (port 8383) | `POST /api/management/v4/catalogs/query/count` (management, port 8181) |
  | federated catalog `POST /api/catalog/v1alpha/catalog/query` (port 8383) | upstream `POST /api/management/v4/catalogs/request` (port 8181) |
  | control plane `/api/management/v3/contractagreements/retirements[...]` | `/api/management/v4/contractagreements/retirements[...]` |
  | upstream `/api/management/v3/*` (still served by EDC 0.18.1, deprecated) | `/api/management/v4/*` (used by all DSE tools, tests and Bruno) |

  The federated catalog no longer has a `catalog` context: port 8383, `WEB_HTTP_CATALOG_PORT/PATH` and the chart `endpoints.catalog` are gone. The authority DID document must publish `FederatedCatalogService` = `https://<authority>-federatedcatalog:8181/api/management/v4/catalogs/request` (use `syncServices`, see the superuser seed).

  Upstream and DSE v4 responses use the upstream EDC `management/v2` context (`edc:`, `dcat:`, `dct:`) plus only the DSE vocabularies: `skos:`, `prov:`, `adms:` (Event model, PSMP-8266) and `dse-policy:` everywhere, and `dse:` in the federated catalog (as before). Every other term is a full IRI, as upstream returns it. Compared to v3 / `v1alpha`: `odrl:hasPolicy` → `http://www.w3.org/ns/odrl/2/hasPolicy` (also `permission`, `prohibition`, `obligation`, `action`, `constraint`, ...), and the catalog `participantId` is `https://w3id.org/dspace/2025/1/participantId`. The federated catalog count keeps `dse:datasetCount`. The control plane has no `dse` prefix (it never had one, v3 included), so the retirement API returns the reason and the retirement date as full IRIs, unchanged from v3: `https://w3id.org/dse/v0.0.1/ns/reason` and `https://w3id.org/dse/v0.0.1/ns/agreementRetirementDate`; only `agreementId` (v3, `@vocab`) becomes `edc:agreementId`. Requests may still send `dse:reason` with the `dse` prefix declared in their own `@context`. Example count response:

  ```json
  [{ "@type": "dcat:Catalog", "dse:datasetCount": 21,
     "https://w3id.org/dspace/2025/1/participantId": { "@id": "did:web:..." },
     "@context": ["https://w3id.org/edc/connector/management/v2", { "dse": "https://w3id.org/dse/v0.0.1/ns/", "dse-policy": "https://w3id.org/dse/policy/", "...": "..." }] }]
  ```

  **Exception: the control plane `POST /v4/catalogs/request` returns the catalog filter's reply as is** (PSMP-11644 review). It keeps the same signature as the federated catalog query API so the two stay aligned (when EDC-V lands, this DSE extension can be replaced by the upstream endpoint with no client change). There is no path collision: the control-plane launcher excludes the upstream `federated-catalog-api` module, so the upstream `/v4/catalogs/request` handler is not on the control plane's classpath (DSE runs a dedicated federated catalog). The control plane forwards the query to the authority catalog filter (which queries the federated catalog and applies the visibility filter) and returns the filter's status, `Content-Type` and body unchanged, with no JSON-LD post-processing. Its keys are therefore **not** the federated catalog response keys: the filter writes the catalogs with the EDC DSP 2025-1 transformers and compacts them with its `CATALOG_FILTER_API` scope, i.e. the DSP 2025-1 context (`https://w3id.org/dspace/2025/1/context.jsonld`), the EDC dspace context (`https://w3id.org/edc/dspace/v0.0.1`) and the DSE prefixes `dse`, `dse-policy`, `skos`, `prov`, `adms`:

  | Federated catalog `/v4/catalogs/request` (FC service) | Control plane `/v4/catalogs/request` (catalog filter reply) |
  |---|---|
  | `"@type": "dcat:Catalog"`, `"dcat:dataset"`, `"dcat:service"` | `"@type": "Catalog"`, `"dataset"`, `"service"` (always arrays; no `dataset` key when no dataset is visible) |
  | `"https://w3id.org/dspace/2025/1/participantId": {"@id": "did:..."}` | `"participantId": "did:..."` |
  | `"@type": "dcat:Dataset"`, `"edc:id"`, `"edc:description"` | `"@type": "Dataset"`, `"id"`, `"description"` (EDC dspace context terms); other asset properties keep `edc:` / `dct:` / `dcat:` / DSE prefixes |
  | `"http://www.w3.org/ns/odrl/2/hasPolicy": {...}` | `"hasPolicy": [{"@id": ..., "@type": "Offer", "permission": [{"action": "use", "constraint": [{"leftOperand": "dse-policy:Membership", "operator": "eq", "rightOperand": "active"}]}]}]`; empty `prohibition` / `obligation` are omitted; `assigner` / `assignee`, when present, are plain IRIs |
  | `"dcat:distribution"`, `"dct:format": {"@id": ...}`, `"dcat:accessService"`, `"dct:conformsTo"` | `"distribution"`, `"format": "HttpData-PULL"`, `"accessService"`, `"conformsTo"` |

  Status codes of the control plane endpoint: the filter's status, `Content-Type` and body are forwarded as is (before, a filter error became a control plane `500` caused by a JSON parsing exception). The filter answers errors with the EDC JSON error body (`[{"message", "type", "path", "invalidValue"}]`): `400` (`InvalidRequest`) without participant token, `403` (`NotAuthorized`) when the token is rejected; when the federated catalog answers with an error, its status and messages are kept for `400`, `401`, `403` and `409` (the statuses with an upstream EDC exception that keeps the federated catalog messages); any other status (e.g. `404`, `500`, `503`), which has no upstream exception that keeps the federated catalog message (`ObjectNotFoundException` has a fixed text), and an unreachable or unresolvable federated catalog give `502` (`BadGateway`, the message names the federated catalog status); an unexpected filter error is a `500` without EDC error body (Jetty error page). A sort by a field the datasets do not have is a federated catalog `400` (see below), so the filter and the control plane answer `400` (`InvalidRequest`) with the message `Cannot sort by '<field>': field does not exist in Dataset`. The control plane itself returns `400` for an invalid `QuerySpec`, `502` (EDC error body, `"type": "BadGateway"`) when the filter URL cannot be resolved from the authority DID document or the filter cannot be reached, `500` when the control plane cannot obtain its credentials token. Clients of this endpoint (cr-bff, the eonax dataset-portal UI) must read the keys above. See `extensions/control-plane/control-plane-federated-catalog-filter/README.md`.

  v4 is stricter than v3: every request needs `@type` with the **compact** type name (`QuerySpec`, `Criterion`, `ContractRequest`, `PolicyDefinition`, `ContractDefinition`, `TerminateTransfer`; not `*Dto`, not an expanded IRI). The DSE v4 endpoints apply the same check as upstream, before JSON-LD expansion: control plane `POST /v4/catalogs/request`, federated catalog `POST /v4/catalogs/query/count` and `POST /v4/contractagreements/retirements/request` need `@type: QuerySpec`, `POST /v4/contractagreements/retirements` needs `@type: AgreementsRetirementEntry`. A missing `@type`, an expanded IRI or another type returns `400`; on the three query endpoints an empty body is still accepted (default query). The federated catalog `POST /v4/catalogs/request` and `POST /v4/catalogs/query/count` (although the count ignores the sort) also reject a `sortField` that no dataset has, before the query, instead of answering `500` without body: `400` with `[{"message": "Cannot sort by '<field>': field does not exist in Dataset", "type": "ValidationFailure", "path": "sortField", "invalidValue": "<sortField as sent>"}]`. `<field>` is the field without the leading `datasets.`; a key that a dataset map does not have (e.g. `properties.'<IRI>'`) is not an error, as before. The deprecated `POST /v3/catalogs/request` has no request validation, so there it is still a `500`. Federated catalog v4 responses (`/v4/catalogs/*`) are compacted with the `https://w3id.org/edc/connector/management/v2` context: `dcat:dataset`, `dcat:distribution`, `dct:*`, `edc:originator`; the count response is `{"@type": "dcat:Catalog", "dse:datasetCount": n, "https://w3id.org/dspace/2025/1/participantId": {"@id": ...}}`. Clients: cr-bff, the eonax dataset-portal UI, cle-subscription-registry (already v4).
- **Management API `/v4beta` is gone; use `/v4`** (same endpoints, stable). Clients configured for `/v4beta` (e.g. cle-subscription-registry local setup) get 404.
- **Contract requests: do not send `profile` together with `protocol`.** In EDC 0.18 a `profile` field in a `ContractRequest` (v3 and v4) replaces the `protocol` of the negotiation; a non-protocol value (e.g. `https://w3id.org/idsa/DP`) makes the negotiation end `TERMINATED` ("No callback address found for protocol"). Send only `protocol: dataspace-protocol-http:2025-1`.
- **The hashicorp data plane now persists access tokens and data flows**, so in-flight PULL transfers survive data-plane restarts. Tokens issued by 0.7.x were kept in memory only, so **PULL transfers started on 0.7.x must be restarted once** after the cut-over: terminate, then start a new transfer (where the DIDs lose their port, on a new agreement: re-onboarding step 4).
- **Suspend → resume of a transfer does not work on 0.18.1**: the transfer stays `RESUMED` and the provider terminates it. Upstream rewrote the resume protocol ([eclipse-edc/Connector#5709](https://github.com/eclipse-edc/Connector/pull/5709)). Workaround: terminate the transfer and start a new one. Terminate works.
- New columns `claims` (agreement and transfer process) and `data_address_owner` (transfer process) are filled for new records only.
- **DID document services are only written when a participant is created.** Changing `edc.ih.api.superuser.services` (e.g. the `IssuerService` URL above) has no effect on an existing participant, and the Identity API `PATCH …/dids/{did}/endpoints` appends a duplicate instead of replacing in 0.18.1. New option `edc.ih.api.superuser.services.sync` (chart `identityhub.participantcontext.superuser.syncServices`, default `false`): at startup the IdentityHub logs every configured service that differs from its DID document; with `true` it updates them (matched by id) and publishes the document again. Services not in the configuration are never touched. Deploy with `false` first, check the `WARNING` lines in each environment, then enable it. See `extensions/identity-hub/superuser-seed/README.md`.
  - Outside this repository, the services are defined in `eonax-iac-workflows` (`terraform/backend/{authority,participant,issuer-service}/identityhub.tf`, authority `catalog.tf` `local.catalog_url`) and `argocd-content-lifecycle-enabler` (`uat/{authority,participant}/values.yaml`). Update the endpoints there (the authority still points to `/api/catalog/v1alpha/catalog/query`) and set `syncServices` there as well, otherwise the sync never reaches those environments.
  - On a participant, `true` also rewrites its `DSPMessaging` and `CredentialService` entries, which other participants use to reach it: check their warnings before enabling it.
